# M4 architecture and security notes — approvals, outputs and versioning

M4 adds a derived approval gate, customer-backed conflict resolution, revisions after approval, versioned blueprint and test-plan exports built only from approved rules, staleness, document readiness, and a project audit trail. It stops before website import and hardening (M5).

The outputs are **human-facing specifications and manual test cases**. Nothing configures, deploys, executes, or simulates anything; every export and the readiness state say so. Readiness describes the readiness of the *documents*, not a deployed agent.

## The approval gate

`approval_status` is **derived on read** from stored facts (`backend/app/outputs.py: approval_reasons`); no mutable "approved" flag exists, so nothing can set it. A requirement version is `approved` only when all of these hold (the `blockers` list names whichever fail):

| Blocker | Meaning |
|---|---|
| `superseded` | a different version of the requirement is the current one |
| `staff_candidate_review` | not accepted for customer review by staff (M2) |
| `scope_review` | scope not confirmed by staff |
| `verified_evidence` | citations are not all verified (M2) |
| `customer_confirmation` | the customer's confirmation was not recorded |
| `validated_confirmation` | the confirmation does not match this version's wording, or no staff validation backs it |
| `high_conflict` | the version is in an open high-severity conflict |
| `conflict_selected_other_rule` | a resolved conflict selected a different rule |

A customer "confirm" alone never approves (M3 records it; staff validation records the confirmation). Staff alone cannot approve either: there is no route that records a confirmation without a matching customer `confirm`.

## Current version and revisions

`conflicts.current_versions` picks the version each requirement stands on: the latest **confirmed** version if any, else the latest version. Consequently a *pending* revision never displaces an approved rule:

1. `POST /requirements/{id}/revisions` (confirmed baseline only) creates version N+1 (`supersedes_id`, original AI proposal and evidence copied, unconfirmed, staff `pending`). One revision at a time; the wording must differ.
2. The baseline stays approved and the outputs stay current. Readiness reports `pending_revision_count`.
3. The revision is accepted, sent for fresh confirmation (M3), and validated. Only then does it become current, the baseline stops being approved, and every output generated from the old version is **stale**.

Outputs are never rewritten: `artifact_versions` are append-only by database trigger, and regeneration creates version N+1. Staleness is computed by comparing the exact requirement-version ids captured per artifact (`artifact_requirements`) with the currently approved set, so a newly approved rule also makes outputs stale.

## Conflict resolution (customer-backed)

`POST /conflicts/{id}/resolve` records an immutable `conflict_resolutions` row. It requires: an active high-or-other `conflict` group; a **customer answer** (latest version) to a question linked to that conflict; a chosen rule that is a member, current, and itself customer-confirmed; and a rationale. It sets `resolved`, so before M4 `resolved` was never set. The other members are then blocked as `conflict_selected_other_rule`.

Decisions to revisit: (a) mapping the customer's answer to the chosen rule is the reviewer's judgement, recorded in the rationale; the API checks the answer exists, is linked, and is current, not what it says; (b) staff can still *dismiss* a conflict as "not a conflict" (M2 triage, rationale required), which removes it from the blockers; (c) any open high-severity conflict anywhere in the project blocks generation (readiness `blocked`), not only conflicts touching approved rules.

## Exports (`schema_version` 2)

- **Blueprint** (Markdown and JSON): customer and property scope; sections (company, hours/after-hours, FAQs and leasing, maintenance, emergencies/transfers/fallbacks, restrictions/limits, integrations/dependencies, other) populated only from approved data, plus an explicit "not covered by approved data" list; each rule carries scope, conditions, proposed action, `requires_live_system_lookup`, its requirement-version id, the customer-confirmation record (marked as confirmed via bearer link, recipient unverified), any conflict resolution, and **verified source references** (document, version and hash, anchor, exact quote). Requirement-version ids are listed per section.
- **Test plan**: for each approved rule a normal, negative and boundary case, an unresolved-dependency case when a live lookup is required, and a case for every unresolved exclusion; each links the requirement version and its source. Manual only: no execution, pass/fail history, or simulation.
- Both list unresolved conflicts, gaps and unapproved candidates as **exclusions**; generation requires the reviewer to acknowledge them. Generation takes a project row lock to number versions safely.
- Export downloads (`/export/md|json`) are audited (`artifact.exported`) as well as generation.

## Readiness and audit

States: `intake`, `extracting`, `in_review`, `awaiting_customer`, `drafting_artifacts`, `artifacts_current`, `artifacts_stale`, `blocked`, computed on read (`GET /readiness`, and the project's `readiness` field). `GET /audit` lists project audit events newest first (staff decisions, customer replies by unverified link, validations, resolutions, generation and exports) with actor labels.

## Authorization and limits

Every route authenticates and checks project membership first; records are fetched with their `project_id`; cross-project ids return 404. Any project member can validate, resolve, revise and generate: the PRD's manager-only final sign-off is **not** enforced. Approval is re-derived per request, so it costs a handful of queries per candidate (list endpoints share one context). The test plan's example inputs are placeholders for a human tester. Structured categories are mapped to sections by a fixed table; rules in unknown categories go to "Other approved rules" and are never dropped.
