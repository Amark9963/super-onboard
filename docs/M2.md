# M2 architecture and security notes — extraction and internal review

M2 turns parsed source blocks into **candidate requirements** that staff can review, scope, edit, reject, merge, and compare against the source text, and it groups potential conflicts and gaps. It stops before customer clarification, invitations, customer confirmation, approval, blueprints, test plans, and website import (M3–M5).

**Nothing in M2 approves a rule.** Candidates always start as customer `not_confirmed` and staff `pending`. A staff "accept" means *accepted for customer review*; the API and UI report `approval_status: "not_approved"`. No M2 route can set a customer confirmation state, and the AI schema has no review or confirmation fields at all.

## Flow

```text
parsed source version ──► extraction job (pending) ──► worker claims it (row lock, bounded attempts)
      provider.extract(batches of blocks) ──► typed ModelOutput (schema v2, extra fields forbidden)
      ──► deterministic citation check against stored blocks ──► unreviewed candidates
      ──► conflict / variant / gap suggestions ──► staff review (edit, scope, accept-for-review, reject, duplicate, merge)
```

The provider call runs outside any database transaction. Candidates, provenance, evidence, audit rows, and the job's result are written together in one transaction, so a failed attempt leaves no partial candidates. A crashed worker's claim is recovered after `EXTRACTION_STALE_MINUTES` (default 10).

## Providers

| Id | What it is | Availability |
|---|---|---|
| `mock` | Deterministic keyword rules over the text (`backend/app/ai.py`). **Not AI.** Every result carries `simulated: true`, and the UI shows a `SIMULATED` badge on each candidate and job. | Always |
| `openai_compatible` | Structured-output chat completions against `AI_BASE_URL` using `AI_MODEL`. | Only when the deployer sets `AI_API_KEY`. |

The live adapter sends only the blocks of one source version, in bounded batches (`AI_BATCH_CHARS`), plus the project's property/portfolio ids and names. Starting a job with it requires the staff member to acknowledge, per job, that document segments go to a third-party API. The reply is parsed against the same typed schema and then verified like any other output. Errors are mapped to content-free codes (`provider_http_429`, `provider_invalid_output`, ...); response bodies, document text, and the API key are never logged or stored in job rows. Transient errors (network, HTTP 429/5xx, malformed output) retry up to three attempts; auth failures, refusals, and other 4xx fail immediately. A failed job can be retried explicitly, which creates a new job and keeps the failed one.

**The live adapter has been exercised only against a stubbed transport in tests. It has never been run against a real model endpoint**, so no live extraction quality is claimed or measured. The mock results must not be read as evidence of live quality.

### Typed output (schema version 2)

Each candidate has `category` (the 14 PRD categories), `title`, `statement`, `topic` (slug), `scope_type` + `scope_ids`, `conditions`, `proposed_action`, `requires_live_lookup`, `missing_information`, and 1–5 `citations` (`block_id` + verbatim `quoted_text`). Unknown fields, unknown categories, and missing citations are rejected. The wire schema for strict structured output is generated from the same types (`wire_schema()`).

## Citation verification (`backend/app/citations.py`)

A citation is verified only if its `block_id` is a block of the **extracted source version in this project** and its quote is found in that block's captured text:

- `exact`: verbatim substring.
- `normalized`: equal after ignoring case, whitespace runs, and typographic quotes/dashes (spacing the source lacks is *not* ignored). The stored quote is the real source text and the character offsets are real positions in the original block, used for highlighting.
- `invalid`: block missing or from another source version, quote not found, or quote shorter than 8 non-space characters (unless it is the entire block). There is no fuzzy matching.

Page, sheet/cell, line and timecode anchors are always read from the block's own parsed locator at display time; nothing is copied or invented. Invalid citations that point at a real block are stored with `quote_match_state = invalid` and no offsets; citations to nonexistent blocks are kept only in the candidate's `citation_report`. A candidate's `evidence_status` is `verified` (all citations check out), `flagged` (some fail), or `unverifiable` (none check out). Only `verified` candidates can be accepted for customer review and only they take part in conflict suggestions.

**"Verified" means the quote exists where it is cited.** It does not mean the statement is a faithful reading of the quote, that the rule is current, or that the customer approved it. Staff must read the evidence.

Model-supplied scope ids are checked against the project's own properties/portfolios. An invalid scope is replaced by company-wide with a recorded note, and every candidate's scope starts as *not confirmed by staff*; accepting requires an explicit scope confirmation (or an edit that assigns scope).

## Data model changes (migration `0004`)

- `candidate_provenance` (append-only): the job, provider, model, `simulated` flag, schema version, and a de-duplication fingerprint per candidate. Re-running extraction on an unchanged source creates nothing new.
- `requirement_duplicates` (append-only): final duplicate/merged decisions.
- `requirement_versions.ai_proposal` is write-once (database trigger on both SQLite and PostgreSQL). Staff edits change only the working fields and are recorded in `audit_events.detail` with before/after values; the proposal and its evidence stay available beside the edited text. New working-field columns: `topic`, `scope_reviewed`, `requires_live_lookup`, `missing_information`, `citation_report`.
- `requirement_evidence` gains `char_start`/`char_end`; `jobs` gains `provider` and `summary`; `audit_events` gains `detail`; `conflict_groups` gains `kind`, `title`, `signature`, `triage_state`, `triage_rationale`.
- Staff decisions are `staff_reviews` rows with `candidate_*` decisions. M4 will add its own decision values for reviewing customer confirmations.

## Review semantics

- Edit: allowed while the candidate is unconfirmed and not rejected/duplicate; an edit to an accepted candidate returns it to *awaiting review*.
- Accept for customer review: pending only, evidence must be `verified`, scope must be confirmed.
- Reject requires a reason; reopen returns a rejected or accepted candidate to pending.
- Duplicate and merge are final. Merge requires identical scope and copies only valid evidence to the target.
- Every decision writes an audit event with the acting staff member; staff reviews hold the rationale.

## Conflicts, variants and gaps (`backend/app/conflicts.py`)

Suggestions only, recomputed after extraction and after every review decision:

- Comparable rules share category and topic, both state a `proposed_action`, and have equal or nested condition sets.
- Differing actions with **overlapping scope** are a potential conflict (identical scope + identical conditions = high; one relaxed = medium; both relaxed = low). Company-wide overlaps every building; a portfolio overlaps its own buildings.
- Differing actions on **non-overlapping scopes** (for example two buildings' pet limits) are `variant` groups labeled as allowed variations, never as contradictions.
- Gaps: candidate `missing_information`, `requires_live_lookup` dependencies, and topics that exist only at narrower scope and miss some buildings.

Staff triage is a classification (`open`, `confirmed` = needs customer clarification, `dismissed` with a required rationale), not a resolution; `resolved` is never set in M2. Group signatures include member substance, so editing a member makes the old suggestion `obsolete` instead of silently reusing a dismissal.

**Limits:** matching depends on the provider's `topic` and `proposed_action` slugs. Two phrasings of the same action can look like a conflict (false positive), and a live model that names topics inconsistently can hide one (false negative). Comparisons are per candidate pair and not transitive. Rules with no stated action are never compared.

## Authorization

Every route authenticates the session and checks project membership before touching data (admins included). Records are fetched with their `project_id`, so another project's job, candidate, or conflict id returns 404 even through a project the caller can access. Cross-project references (duplicate target, scope ids, source versions) are rejected, and composite foreign keys backstop writes. Mutations require the existing Origin and CSRF checks.

## Not in M2

Attaching new evidence to a flagged candidate, undoing duplicate/merge, resolving a conflict, customer questions or confirmations, approval transitions, OCR, and website import. Extraction is per source version; there is no cross-document model prompt, so cross-source conflicts are found by the deterministic grouping above, not by the model.
