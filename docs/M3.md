# M3 architecture and security notes — customer review

M3 lets staff send customers a login-free link to confirm proposed rules and answer clarification questions, receive their (partial, versioned) responses in an internal inbox, and record a customer confirmation. It stops before blueprint/test-plan generation, readiness/staleness and the final approval gate (M4), and website import (M5).

**Nothing in M3 approves a rule for a blueprint.** A customer's "confirm" changes nothing by itself. A staff member must validate it, and only validation records the customer confirmation. API responses keep reporting `approval_status: "not_approved"`; M4 owns the approval transition (it also needs conflict resolution and reviewer sign-off).

## Flow

```text
accepted candidate (M2) ─┐
conflict / question ─────┴─► composer ► draft + preview ► send ► login-free link (+ email)
      customer: confirm | request correction | cannot confirm | answer (partial, idempotent, amendable)
      ► inbox ► staff validates / rejects the confirmation / acknowledges / revises from a correction
```

## Composer, preview and snapshots

- Eligible rules: accepted for customer review, evidence fully verified, scope confirmed, not already confirmed. Staff may add questions (free text, yes/no, single or multiple choice), optionally linked to a requirement or conflict.
- Each item is frozen as an immutable `review_request_items.shared_payload` snapshot: the question, the rule's wording/scope/conditions/action as proposed, and only the **verified evidence excerpts staff selected**. The staff preview and the public page render the same `customer_view`, built only from those snapshots, so staff preview exactly what the customer receives. It carries no project/requirement/evidence ids, AI labels, staff emails or internal notes.
- Wording is frozen while a link is live: an active, unexpired invitation blocks editing, rejecting, reopening, duplicating or merging the candidates it asks about (revoke first). Sending also re-checks that the wording still matches the draft's snapshot.

## Links and email

- 256-bit random tokens (`secrets.token_urlsafe(32)`); only the SHA-256 hash is stored and the raw token is shown once in the send/resend response (copy-link fallback). A draft's token hash is a random placeholder: no link exists until it is sent.
- Lifecycle: `draft → active → expired | revoked`. Default 7 days, 1–30 configurable. Expiry is enforced server-side from the stored timestamp. *Resend* creates a fresh invitation and revokes the old one in the same transaction; a resent link shows the earlier answers.
- Email goes through SMTP (Mailpit locally; set `SMTP_*` for a relay). The email carries the organization, request name, item count, expiry and link, never rule text. Delivery states are honest: `smtp_accepted` (the server took it; inbox delivery is **not** confirmed), `failed` (with a content-free code), `link_only` (no email requested). Header injection is prevented by collapsing whitespace in subjects.
- The public API logs nothing token-bearing: the backend runs with `--no-access-log` because review URLs carry the token in their path. `Referrer-Policy: no-referrer`, `Cache-Control: no-store` and `X-Robots-Tag: noindex` are set on public API and page responses, and the page loads no third-party resources.

## Public routes (`/api/public/review/{token}`)

- Token-only scope: a token reads and writes exactly the items listed for its invitation. Unknown or malformed tokens return the same 404; known-but-expired/revoked tokens return 410 with a generic message. Invalid-token guesses share a global DB-backed rate limit; valid tokens are limited per invitation. Public routes accept no cookies or internal sessions.
- Responses: `answer`, `confirm`, `request_correction`, `cannot_confirm`, validated per item (allowed types, exact answer fields, offered choices, bounded lengths, unknown fields rejected). A request is validated whole before anything is stored.
- Idempotency: the client sends a `submission_id`. Replaying it returns the stored result without creating another row (unique per invitation/item/submission); a new id amends and creates version N+1. Concurrent conflicts are retried. Partial submissions are fine; the page reports what is outstanding.
- Items already confirmed and validated by staff are locked for the customer.
- Audit events use actor type `customer_link` referencing the invitation id, never the token. A link holder is an unverified capability holder, not a verified person.

## Confirmation workflow (two separate axes)

1. **Customer axis:** the customer's response versions (append-only). The inbox shows the latest version per item, the previous one, the unverified recipient, and the next action.
2. **Staff axis:** `validate_confirmation`, `reject_confirmation` (reason required) and `acknowledge`. Validation needs: the latest response is a `confirm` for a `confirm_rule` item, the candidate is still accepted and unconfirmed, and the live wording equals the snapshot the customer saw. It then writes a `customer_confirmations` row (the exact snapshot wording), sets the version's `customer_confirmation_state` to `confirmed` (the existing trigger freezes it) and a `staff_reviews` row, and audits `confirmation.validated` with the note "confirmed via bearer review link; recipient identity not verified". Staff cannot create a confirmation without a matching customer `confirm`.
- `customer_confirmation_state = confirmed` therefore means *a customer confirmation was recorded **and** accepted by staff*. A pending customer confirmation is visible in the inbox, not on the version. Rejecting a confirmation leaves the version unconfirmed; the customer can amend, and the older response can no longer be validated.
- **Correction requests:** staff use *Revise from correction* to create version N+1 (supersedes the old one, copies the evidence and original AI proposal, `pending` again). The old version is rejected as superseded. The revision must be re-accepted and re-confirmed from a fresh request; a stale `confirm` for the old wording can never be validated.

## Data model changes (migration `0005`)

Added columns only (existing immutability triggers are untouched): request `message`/`created_by`; question `conflict_id`; invitation `activated_at`, `revoked_at`, `opened_at`, `sent_at`, `delivery_error`, `replaces_id`, `created_by`; `staff_reviews.response_id`; a unique index so each requirement version has at most one customer confirmation. The M0 tables for requests, items, invitations, responses and confirmations are now exercised end to end.

## Limits and decisions to revisit

- Bearer links only: no OTP or identity verification. Forwarded links work for whoever holds them until expiry or revocation.
- Email is sent synchronously inside the request with a short timeout; there is no retry queue, no bounce handling, and no automatic reminders (manual resend only, per PRD P0).
- A validated confirmation freezes the version. Changing it later is the M4 revision flow; M3 only supports revision after a correction request.
- Rate limits are per-token and global-invalid, not per client IP (the reverse proxy would need trusted forwarded headers).
- Customer comments are stored and displayed as plain text. Do not paste secrets into review pages.
